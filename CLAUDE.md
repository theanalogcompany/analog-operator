# analog-operator

The operator-facing native mobile app for Analog — a guest recognition platform for independent cafes, bakeries, and restaurants. The operator uses this app to review and approve AI-drafted iMessage/SMS replies before they ship to guests. The actual messaging engine lives in the sibling `analog-guest` repo; this app consumes operator-facing API endpoints from there.

## Stack

- Expo SDK (latest stable) + React Native + TypeScript
- expo-router (file-based routing)
- NativeWind (Tailwind-for-RN) for styling
- react-native-reanimated + react-native-gesture-handler for animation/gesture primitives
- react-native-svg (the Instagram glyph and the copy icon) + expo-clipboard (TAC-486). Both are in the Expo SDK, so Expo Go still works.
- expo-font for custom font loading
- Supabase JS client (for auth session management; the database itself lives behind `analog-guest`'s API)

## API consumption

- This app calls operator-facing endpoints in `analog-guest`. Spec lives in Linear ticket TAC-258.
- Base URL via env var: `EXPO_PUBLIC_API_BASE_URL` (e.g. `https://analog-guest.vercel.app`)
- **Fixture mode: when `EXPO_PUBLIC_USE_FIXTURES === 'true'`, `lib/api/queue.ts` and `lib/realtime/queue-channel.ts` route to in-memory fixtures (`lib/fixtures/queue.ts`).** Strict-true gating — `false`, `0`, or unset all mean live mode. Live mode requires `EXPO_PUBLIC_API_BASE_URL`; missing → `authedFetch` returns `NO_SESSION`. Use fixture mode for offline dev / storybook work; leave unset elsewhere. (Originally gated on `!EXPO_PUBLIC_API_BASE_URL` during the parallel-build phase; flipped during TAC-270 cutover so prod and CI never accidentally fall back to fixtures when the API URL is misconfigured.)
- Supabase env vars: `EXPO_PUBLIC_SUPABASE_URL` + `EXPO_PUBLIC_SUPABASE_ANON_KEY` (required; `lib/supabase/client.ts` throws at module load if either is missing). Copy `.env.example` → `.env.local` and fill.
- Auth: Supabase session JWT in `Authorization: Bearer <token>` header — wired via `authedFetch` in `lib/api/client.ts`. One refresh-and-retry on 401/403, then `NO_SESSION`. Never loops. API client never navigates; auth redirects belong to the global session listener.
- Errors-as-values shape: every `lib/api/*` function returns `{ ok: true, data }` or `{ ok: false, error: ApiError }`. `ApiError` is one of `NO_SESSION | HTTP | NETWORK | PARSE`. Current callers treat all `HTTP` as retryable — comment in `parseHttpError` if that taxonomy needs to grow.

## Cross-repo contracts

This app and `analog-guest` ship features together — operator endpoints land server-side first, then the client consumes them. Every cross-repo ticket pair (sibling pattern, e.g. TAC-207 ↔ TAC-288) follows these rules. Background: the TAC-207/TAC-288 push-notifications build burned 9 hours of debugging across multiple sessions because the client and server each implemented their own internally-consistent interpretation of an unwritten contract. These rules exist to prevent the next instance of that.

1. **The `## Contract` section is the single source of truth.** Any cross-repo ticket MUST contain a `## Contract` block in the ticket description that locks: endpoint path (character-exact, including singular vs plural, leading slash), request body shape with a concrete example, response shape per status code, and required env vars with format notes (e.g. base64-DER vs raw, with-or-without dashes, plaintext vs JSON-string-escaped). If the Contract lives on one sibling, the other ticket links to it. Treat this section as authoritative — code matches the Contract, not the other way around.

2. **No silent divergence.** If implementation needs to deviate from the Contract to match a codebase convention (singular `operator/` vs plural, snake_case vs camelCase, etc.), the ticket description is updated FIRST during plan review; the sibling ticket is updated in lockstep. Implementation never silently diverges with an "I chose X to match convention" justification while the Contract still says Y. The Contract reflects the decision, then code lands.

3. **Server-first, sequential rollout.** Before touching client code in `analog-operator`, the `analog-guest` endpoint must be deployed AND verified via `curl` against the Contract section's exact request shape. Parallel development against an unverified contract is the documented root cause of the TAC-207/TAC-288 debugging sessions. The tolerant-Zod pattern under "Common gotchas" is the narrow exception (additive nullable fields), not a license to develop both sides in parallel.

4. **Manual end-to-end UAT is a Done gate.** Unit tests passing on both sides proves each side is internally consistent with its own assumption of the contract — it does not prove the assumptions match. A cross-repo ticket cannot move to Done on unit-test pass alone; the operator runs the cross-repo flow on device (TestFlight for push, dev client for native-module paths) and confirms behavior end-to-end before close. UAT is NOT deferred to the sibling ticket — both tickets share the gate.

5. **Contract-boundary tests assert against the Contract's literal payload, never against the code's own serialization.** A test written by reading the implementation is worthless for cross-repo agreement — it can only ever confirm the code does what the code does. When you write or edit an assertion on a request body, response shape, endpoint path, or header that crosses the repo boundary, the expected value is transcribed from the ticket's `## Contract` block. Not from the function you just wrote, not from a passing run's actual output, not from memory. If the Contract isn't reachable, that is a blocker to raise — never a licence to assert what the code happens to emit.

   This has now cost us twice. TAC-207/TAC-288 burned 9 hours on two internally-consistent readings of an unwritten contract. TAC-310 was worse: `__tests__/lib/api-queue.test.ts` asserted `toEqual({ body: 'my version' })` against a client that posted `{ body }` while the server read `editedBody`. The test didn't miss the defect — it **certified** it, and kept certifying it on every green CI run while five operator sends failed in production. Both sides green, both sides wrong, no signal anywhere.

   Corollary: a test that mocks or bypasses the network layer cannot make a contract claim at all. In `analog-operator`, fixture mode short-circuits before `authedFetch`, so nothing in a fixture-mode block observes a URL, method, header, or body — wire-shape assertions must live in a live-mode block with `fetch` mocked. Putting a send-path assertion in the fixture block yields a passing test that asserts nothing about what ships. (TAC-310.)

6. **A Contract names every party that reads the payload, including the ones neither team wrote.** A client library sitting between the two repos is a party. TAC-207 #7 and TAC-288 #4 both specified APNs custom data as top-level `draftId` / `guestId` / `operatorId`; `analog-guest` sent exactly that and `analog-operator` read exactly that. Both sides agreed with each other AND with the ticket, and all three were wrong together, because `expo-notifications` hands JS `userInfo["body"]` rather than the whole `userInfo`. Every draft and arrival push was undeliverable to the tap handler from the day push routing shipped until TAC-419, and nothing anywhere went red — the push displayed, the badge updated, and every test hand-fed `content.data`, so nothing ever crossed the serializer.

   The rule that would have caught it: when a payload passes through a third-party SDK, the Contract states what that SDK does to it, with the version pinned and the source line cited. "Both repos implement the Contract" is not the same as "the payload arrives". Where the SDK's behaviour is load-bearing, pin it with a test that reads the installed source — `__tests__/lib/notifications-serializer-contract.test.ts` is the worked example. (TAC-419.)

## High-stakes flags

**High-stakes changes are planned before they are built, and the narrowest of them are never built unattended.** **Hard stop** — auth (Supabase session, JWT handling, deep link callbacks), anything that sends a message via the API (operator approve/edit/skip/undo, which reaches Sendblue downstream), anything that writes to operator's session storage (Expo SecureStore), or anything touching push notification entitlements or APNs configuration. Write the full plan and post it as `[PLAN]`; on approval post `[HUMAN-REVIEW-REQUIRED]` and stop, because the build is a session Jaipal drives. **Plan gate** — anything else this repo calls high-stakes, which in `analog-operator` is currently nothing: the hard-stop list above is its whole high-stakes list. Write the full plan, post it as `[PLAN]`, wait for approval, then build, commit, push and open a draft PR. Neither tier is a reason to skip the plan, and neither proceeds via `[NEEDS-INPUT]` alone. A change to guest-facing copy shows the new wording verbatim in the plan and waits for approval of that wording specifically.

The list is per-repo on purpose: it names what can reach a guest, move money, or destroy data *in this repo*. `analog-guest`'s is different (Stripe, Sendblue webhook handlers, migrations, the agent runtime contract) and neither should be copied into the other. `.claude/process.md`, "High-stakes work: a plan gate, and a narrower hard stop", is canonical and is shared text.

## Common gotchas

- **A workflow change cannot be tested before it merges, so `__tests__/workflows.test.ts` is the only gate that can fail first.** `claude-code-action` skips itself when its workflow file differs from `main`'s copy and exits green, so a green `check` on a PR that edits `.github/workflows/*` proves the session skipped, not that the change works (`build-ready.yml`'s header records this; run 35149594063 is the example). Scheduled workflows also only ever run from the default branch. The test does statically what CI cannot do at all: it parses both workflow YAMLs, asserts the three shared repo-rule jq defs (`repo_labels`, `repo_line_names`, `owner`) are character-identical between `build-ready.yml` and `audit-new-todo.yml`, and runs the workflows' **own extracted jq** over synthetic tickets — never a TypeScript reimplementation, which could only confirm the test agrees with itself. `npm run validate:workflows` runs just that file. It needs `jq` on PATH (present on `ubuntu-latest`, and required rather than skipped if absent). **It passes the jq program as a temp file, never `-f /dev/stdin`** — `execFileSync`'s `input` gives the child a pipe, which macOS opens happily through `/dev/stdin` and Linux refuses with ENXIO (`jq: Could not open /dev/stdin: No such device or address`), so the first version of this test passed on a Mac and failed all eight of its jq-backed cases in CI. `.nvmrc` pins the Node major but nothing pins the kernel: a test that shells out is the one kind that can still diverge between a local run and CI after TAC-427's guard, so verify one in CI rather than locally. Those defs are also shared with `analog-guest` and must be copied verbatim between the repos; nothing here can check that, because a run reaches only its own repo. (TAC-439.) It also runs `build-ready.yml`'s `SELECTED` program over blocked tickets to pin which newest comment resumes one. Claude Code's own `[AUDIT]` doesn't. Any comment without the CC prefix does, whether it is a `**[FROM CLAUDE CHAT — RULING` comment, a plain `**[FROM CLAUDE CHAT]**` note or an unprefixed reply: the jq gate is coarse, as TAC-396's approval left it. The session it starts is finer: `.claude/process.md`'s "Comments" section has it read a plain `[FROM CLAUDE CHAT]` note as context that advances nothing, and an escaped CC prefix as Claude Code's own (TAC-454). One case, named `KNOWN GAP`, asserts today's wrong behaviour on purpose. `is_bot` doesn't unescape `\[`, so the jq reads an escaped CC prefix as human and resumes. `RULES` is shared with guest, so a fix lands in both repos or neither. Fixing it turns that test red; flip its expectation then. (TAC-437.) It also checks that each workflow's allowlist admits every `node scripts/linear.mjs` call its prompt teaches, and that its disallow list doesn't block one (TAC-451). And it runs the `[DENIALS]` capture block's two jq programs, over fake secrets and over each real workflow file (TAC-441; see the `[DENIALS]` entry below).
- **In CI, an allowlisted shell tool is still refused on a file outside the checkout (TAC-451, adopting TAC-444).** Established in `analog-guest`, and the prompt text is shared with it. Claude Code checks the file arguments of a fixed set of commands (`jq`, `rg`, `grep`, `cat`, `wc`, `sed`, `head`, `tail`, `cd`, `ls`, `find`, `awk`, `diff`, `git` and more). A path outside the working directories resolves to "ask", which an allow rule such as `Bash(jq:*)` cannot override, and in a headless session "ask" is a refusal. An output redirect to a path outside the checkout is checked the same way. A pipeline or `&&` chain is refused whole if any part of it is refused. `curl`, `node` and `python3` are not in that set, which is why `curl -d @<file>` and `node scripts/linear.mjs comment <issue> <file>` pass on a file in the runner temp folder while `jq … <the same file>` is refused. **Not path-checked is not the same as allowed.** Here `node` passes only as `node scripts/linear.mjs`, the one entry both allowlists carry (see the `scripts/linear.mjs` entry above); any other `node`, and all of `python3`, is refused on the allowlist. `${{ runner.temp }}` (`/home/runner/work/_temp`) and the files Claude Code saves a large tool result to are both outside the checkout. Evidence, all from `analog-guest`: its run 35271049290 refused `jq -Rs '{a:1}' /home/runner/work/_temp/…` with nothing else in the command. Three of its build runs (TAC-428, TAC-396, TAC-325) were refused the same way trying to JSON-encode a plan file with `jq`. Source: Claude Code 2.1.273's permission code, while CI ran 2.1.275, so re-check after a CLI upgrade. Related, from the same source: the Write tool fails when it overwrites an existing file outside the checkout that the session hasn't read, which is why both prompts say to give every write its own file name. **Before blaming a refused command's flags, pipe or `&&` shape, check whether any part of it is a path-checked tool touching a file outside the checkout, or a tool this workflow's allowlist doesn't carry.** In this repo that includes `wc`, `cat`, `find`, `ls` and `python3` on both, and `node` beyond the helper.
- **`[DENIALS]` redacts every secret its step holds, and reads which ones from the workflow file (TAC-441).** The capture block in both workflows (it opens `# What the session did`) reads its own workflow with `git show "$GITHUB_WORKFLOW_SHA:<path>"`, never the working tree, because a build session leaves the checkout on another branch. It takes every `NAME:` line whose value opens with a `${{ secrets.* }}` or `${{ github.token }}` expression, which also catches `with:` inputs, never set as env vars. For each `NAME` set in the step's environment it redacts the value, both raw and JSON-escaped, since a tool input with no command or file path is printed as JSON. So a secret added to the step later is covered with no list to update. Four rules, each with a test in `__tests__/workflows.test.ts`:
  1. **A secret must be the whole value of its env entry.** `AUTH: Bearer ${{ secrets.X }}` holds the secret inside a longer string, so redacting `AUTH`'s value misses the secret typed alone. The test fails on one.
  2. **Redaction runs before whitespace is collapsed and before the 2000-character cut.** Collapse first and a multi-line secret no longer matches; cut first and a secret across the cut is half shown.
  3. **An empty or blank value is skipped.** It would otherwise reach `split("")` and break every line apart.
  4. **Nothing to redact against means nothing is posted.** If the step finds no secret, because `git show` failed or the pattern stopped matching, it withholds the commands and posts only the count. Posting them would drop even the Linear-key redaction every run has had.

  **The live record is audit run 35306256155 on fixture TAC-464.** A throwaway branch declared `DENIALS_CANARY: ${{ secrets.DENIALS_CANARY || '<fake value>' }}` in the reporting step. No repo secret has that name, so the step held the fake value under a `secrets.*` declaration. The session was refused `python3 -c "print('tac441-left <fake value> tac441-right')"`, and `[DENIALS]` posted it as `python3 -c "print('tac441-left *** tac441-right')"`. **To make a fixture session hit a denial, put the command in the workflow prompt on the throwaway branch, and use a command that is actually refused.** Two earlier runs missed:
  - A ticket asked for `echo`, which Claude Code allows although it's on neither allowlist, so nothing was refused.
  - A ticket asked for `python3`, and the audit session didn't run it, because `audit-ticket.md` tells it to check a command's behaviour by reading rather than running.

  Only this step's secrets are covered. `CLAUDE_CODE_OAUTH_TOKEN` goes to the Claude step alone, so if a session typed it into a denied command, it would be posted unredacted. The block is character-identical in both workflows, which the test checks, and in `analog-guest`, which nothing here can check: TAC-442 copies it from here.

A git worktree under `.claude/worktrees/` is a full checkout, so without the ignore Jest collects every test in it. That is worse than a slow run: `moduleNameMapper` maps `@/` to *this* checkout's root, so a worktree that has drifted onto another branch runs that branch's tests against this checkout's code, and the suite reports on a mix of two branches. Remove a worktree when its ticket closes (`git worktree remove`). Also delete any `name 2.ts` files you find: the repo lives in an iCloud-synced folder, ` 2` is iCloud's conflict-copy naming, and Jest and `tsc` both collect them. CI runs on a clean checkout and sees neither. (TAC-388: on 2026-09-14 the `tac-364-heads-up` worktree held TAC-364's branch for nine hours and supplied 65 of 130 collected test files.)

Don't soften it to a warning, and don't bypass it by pointing `npx jest` at another Node; install the declared version. `__tests__/jest-node-version.test.ts` pins both the decision and the wiring. **The incident:** TAC-427. - **A double-submit guard is a ref, and only one `act()` scope can test it (TAC-399).** Two calls in the same tick both read React state from before either one's render, so `if (submitting) return` lets both through. On device the two calls come from an autofill event firing twice, or a double tap on Verify with a code kept after a network error. The guard in `app/sign-in/verify.tsx` is a `useRef`, set synchronously before the first `await`. The test trap: each `fireEvent` is its own `act()`, and React commits between them, so the second event meets the disabled input and a state guard passes. Put both events in one `act(() => { fireEvent…; fireEvent…; })` instead. React 19 doesn't flush nested `act` calls until the outer one exits, so the second event runs against the same props and closure as the first. Swapping the ref for state turns both same-tick tests in `__tests__/screens/verify.test.tsx` red. Two corollaries:
  1. `fireEvent` skips a non-editable input and a disabled button, so a test of the guard behind a disabled control calls the prop handler directly.
  2. The guard is released only when verify fails. After a successful verify the server has consumed the code, so the guard stays held through `linkOperator` and on both ways out. Holding it can't strand the screen: success leaves through `Stack.Protected` in `app/_layout.tsx`, and a link failure through `router.replace('/sign-in')`. The hole is not fully closed: the other fields stay required, so a row with a malformed `created_at` or no `venue_id` is still dropped before the condition and removes nothing.

  **Removal is authoritative only against live rows, not against an in-flight fetch.** `reconcileFetchedThread` takes the server response wholesale, so a row removed during the mount-time fetch window is re-added if the response still carries it — the server's snapshot predates the change. It self-corrects on the next live event for that row and degrades to pre-TAC-411 behaviour meanwhile, so it was left alone deliberately: a `removedIds` ref that suppressed the id would permanently hide a `failed` send that later retried to `sent`. Known window, recorded rather than fixed (TAC-411 review).

  **The conversations list has two branches, and they are not one rule with a different preview.** A guest with at least one counting message has `lastMessageAt`, `lastMessageDirection` *and* `lastMessagePreview` all describing their newest **counting** message — a newer unsent draft does not move the row. A guest with none gets `lastMessagePreview: ""` with the other fields from their newest non-empty message whatever its state, so the row still sorts by the draft's time and the direction is usually `outbound`. `ConversationRow` renders no speaker and no dash for an empty preview (the direction came from an unsent draft, so naming one would claim someone said something), holding the line's height so the banded rows keep their rhythm; `app/conversations/[guestId].tsx` builds no fallback bubble for it and shows `EmptyState variant="thread"` instead. That copy is **"Nothing has reached this guest yet."** and deliberately not "No messages yet" — an operator holding a pending card for that guest would be told nothing exists while the card in their hand says otherwise.

  **Both thread surfaces carry that empty state, and must keep answering the same question the same way.** TAC-395 also made a zero-bubble *edit takeover* reachable — a guest whose only inbound was media-only has `body: ''`, which fails condition 1, so `recentContext` and the thread endpoint are both empty and the thread area above the composer sat blank, reading as a screen that failed to load. `app/queue/edit.tsx` renders the same `EmptyState variant="thread"`, **with `backed`**: the line is white 32px, which is large text and so needs 3:1, but on Honey it measures 2.62:1 and Honey holds 3:1 only to y=420 while the takeover's thread area centres below that. It sits on `dividerBacking`, the same scrim the takeover's date dividers use, rather than a second token. The Conversations thread passes no `backed` — clay clears the bar unbacked, the same reason `surface="thread"` has no divider pill. `__tests__/lib/ground-contrast.test.ts` gates both and records the unbacked Honey figure, so a ground change forces a re-read (SR-1). Two things it is not: an empty *draft* is a different state with its own composer placeholder (TAC-310) and says nothing about the guest; and an empty-bodied `recentContext` entry still draws a blank bubble per the ruling above, so the thread is not empty and the empty state must not claim it is. **On the takeover the error branch needs a second guard.** On `kind: 'error'` the screen keeps its `recentContext` seed, and for a draft out of the queue cache that seed is the server's own answer to the same question, so an empty one supports the claim. A **decline handoff's** seed is not: `lib/decline-handoff.ts` hardcodes `recentContext: []` as a placeholder meaning *unknown*, for a guest the agent has by construction already promised something to. Without the guard, swipe-left on a heads-up card plus any `getThread` failure claims nothing reached a guest, directly above an apology addressed to them. `showEmptyThread` therefore only claims on error when the seed came from the server. If you add another fabricated `PendingDraft`, it needs the same treatment. **Both screens also gate the claim on `kind !== 'loading'`** — it is an assertion about the guest, and an unresolved fetch has not established it; without the gate the screen asserts it on mount and then replaces it with bubbles. Each gate has its own test, because the first version of them did not and the mutation survived. `lib/fixtures/conversations.ts` models the whole thing with `SeedMessage.unsent`, the only way to seed an empty preview when the preview is derived from a message body.

- **Instagram's reply window: one pure function, one clock, and a 5-minute margin the server does not apply (TAC-486).** TAC-473's Contract sends `replyWindowExpiresAt` as the TRUE deadline, Meta's clock, with no margin, and says explicitly that the client subtracts its own. The server's send gate already refuses inside `INSTAGRAM_WINDOW_MARGIN_MS` (5 minutes), so rendering the raw value shows ~5 minutes in which a swipe-right looks available and dies at the gate. `DISPLAY_MARGIN_MS` in `lib/reply-window.ts` mirrors it; if the server's changes, this changes with it. `windowState` returns SIX kinds, not the design's four (`none`, `unknown`, `plenty`, `close`, `urgent`, `closed`): `'none'` (a text guest has no window) and `'unknown'` (an Instagram guest whose window nobody measured) are kept apart because the Contract insists on it, and an `'unknown'` card must never render as expired — that tells the operator a reachable guest is out of reach. An unparseable deadline fails toward `'unknown'` for the same reason. Labels round DOWN, always. `hooks/use-now.ts` is ONE module-level 60s ticker with a subscriber refcount, not an interval per card: `FrontCard` is keyed by item and remounts on every swipe, so a per-card interval restarts its minute each time, and a module clock is also what makes two cards on screen agree about what time it is. Disposed at zero subscribers and re-armed on mount, per the module-timer rule above (TAC-266); it also refreshes on foreground, because `setInterval` does not reliably fire while backgrounded.
- **An expired card is rendered OUTSIDE the `GestureDetector`, and Jest cannot see that (TAC-486).** Once the window shuts, swipe is gone in both directions and the card's one action is a real `Pressable` (copy the draft, open the guest's thread). Those two facts are the same fact: a `Pressable` inside a `GestureDetector` wins RN's responder race and kills both the pan and the tap (TAC-37), so the only arrangement that gives a genuinely pressable button is no detector at all. It also makes "this card cannot be swiped" structural rather than a flag someone can flip. **A probe comparing the rendered host-component types of a live card and an expired one found them identical** — `GestureDetector` contributes no host node — so that half is carried by the code and by device UAT, and the tests assert the second guard instead: the stack hands the gesture `enabled: false` and `canCommitRight: false`, and `swipeActionFor` refuses every `SwipeOutcome`. That second guard is the one that covers what structure cannot anyway: a card that expires WHILE a pan is in flight, which is cancelled, reset and explained (ruled 2026-09-23 — the card converts the moment it expires, even mid-read, which the margin makes safe because ~5 real minutes of window remain at conversion). `swipeActionFor` and `canCommitRightFor` take a REQUIRED `SwipeContext`, so a new call site cannot silently default to "still open". **The swipe is not the only send path.** A takeover opened while the window was still open outlives that decision entirely, and a long edit outlasts the 5-minute margin easily, so `handleSend` in `app/queue/edit.tsx` re-checks the window at press time; without it the send goes out, the server 502s for a closed Instagram window, and the operator gets a generic failure toast that says nothing about why.
- **`HandleLink` has two modes and no default, because the wrong one fails silently (TAC-486).** `button` is a real `Pressable`, safe only where no `GestureDetector` is an ancestor: the Texts thread header, and the expired card. `hoisted` renders an inert, `collapsable={false}` view the stack MEASURES on the UI thread when a tap lands. Pick wrong and the pan dies on every card while the component still renders and every unit test still passes. **It is not the same treatment the composer gets, and saying it was is what hid a defect for a whole review cycle.** The first version compared an `onLayout` rect against the gesture's card-local `event.x/y` — but `onLayout` reports coordinates relative to the IMMEDIATE PARENT, and the handle sits three levels inside the head, so its rect came back at about (0, 0). The real handle never matched and a tap on the FLAG STRIP opened Instagram. `isComposerTap` gets away with a card-local `y` only because the composer happens to be a direct child of the card's inner column. Both sides are now page coordinates: `measure()` against the gesture's `absoluteX/absoluteY`, with no arithmetic in between. `isHandleTap` needs a full rectangle rather than one boundary, takes a `hitSlop` (the handle is ~16pt tall, well under Apple's 44), and refuses any rect with no area. Tapping the handle OPENS and does nothing else — deliberately not the copy button's action, since replacing an operator's clipboard because they looked at who a guest is, is a side effect they never asked for.
- **What a guest is called lives in `lib/guest-identity.ts`, and the old chain rendered BLANK (TAC-486).** `phoneFallback` / `guestPhoneFallback` is a non-nullable string that is `''` for a phoneless guest (ruled in TAC-473, so one Instagram guest cannot empty the queue for a whole venue), and `??` does not fall back on `''` — so `name ?? phoneFallback` printed nothing at all for an unnamed Instagram guest. That was live on the queue card, the conversation row, the edit takeover's header and the undo toast; all four now route through one chain. The order is name, then **the channel's own** identifier, then a plain fallback (`Instagram guest` / `Guest`). Channel-specific rather than handle-then-phone in one order: a card's identity has to agree with what approving it will do, the same reason TAC-473 makes `guestChannel` the draft row's own channel, and a guest holding both identifiers on the text channel gets a message at their phone. A handle standing in for a name keeps its own case and tracking rather than becoming tracked caps — nobody can look up `@LENA.EATS`.
- **`slate` is a `GroundName` but NOT a `CardGroundName` (TAC-486).** A card ground names a kind of DECISION, and "the reply window closed" is not one: an expired card keeps its bucket and wears slate over the top, so slate is an override rather than a bucket. Adding it to `CardGroundName` would let `bucketForItem` return it, and every `it.each(CARD_GROUND_NAMES)` in `ground-contrast.test.ts` would silently start covering a ground that has its own explicit rows — which is how two sets of figures drift apart with nothing failing. `grounds.test.ts` pins the separation. Its strip is `EXPIRED_STRIP_COLOR` (`#1C1814`), its own constant for the same reason: `STRIP_COLORS` is keyed by `CardGroundName`. **The hand-off contradicts itself on that value** — README A3 says `#2B2926`, README A4's table and the artwork say `#1C1814` — and A4 won (ruled 2026-09-23).
- **The queue is ordered by TIME LEFT, and that changed observable order (TAC-486).** Ruled 2026-09-23. `sortByPriority` in `hooks/use-queue.ts` used to sort by recognition tier FIRST, so a raving fan with twenty hours sat above a new guest with forty minutes and the queue buried exactly the card about to become unsendable. Tier is now a tiebreak within equal urgency. The ticket's own note said this would be a no-op, and it was wrong about this codebase: it was true of the SERVER's order, but the client re-sorts. It sorts by GUEST rather than by card, which is what makes a guest's cards consecutive IN THE SORT — the sub-queue row ("2 / 3 cards for Mia") claims they sit together, and a per-card comparator makes that usually true and unties whenever another guest's card lands between them. One thing does still split them, and the row's claim is absolute where it should not be: `surfaceTappedItem` lifts a notification-tapped card to the front of `displayItems`, which is the same list `subQueuePositionFor` counts. So a push tap on the second of a guest's three cards puts it first and leaves the other two behind it. Narrow, recorded rather than fixed. Cards with no window sort last as a group. The sub-queue row derives its position AND total from the deck, never from `otherPendingDraftsForGuest`, which is a count and cannot give a position; the deck is venue-filtered and reflects optimistic removals, so sending one of three renumbers the rest immediately.
- **The reason-code map now has a completeness test, and SIX CODES ARE STILL UNMAPPED (TAC-486, carrying TAC-511).** `lib/review-bucket.ts` holds two lists, transcribed from `analog-guest`'s `REVIEW_REASON_LABELS` on its merged `main`, 2026-09-23, which had 26 codes. `SERVER_REASON_CODES` is the 25 we have ruled a bucket for, and a test asserts each has an EXPLICIT bucket rather than falling through to `FALLBACK_BUCKET`. `UNRULED_SERVER_REASON_CODES` holds the ONE code that is deliberately not a bucket at all. **`instagram_send_failed` is not a draft-review reason** — the message already failed to send, so there is nothing to approve, while every bucket names a kind of decision about a draft still about to go out. Ruled 2026-09-23 that its operator action is an expired card's (get the text out by hand) and it belongs on the slate ground with the copy-and-open block. It is left unmapped rather than forced onto the expired card, because three things there would be false for it: the strip says "Reply window closed" and a send can fail with the window wide open, the body line names a specific wrong reason, and the timer would read "18h left" above a block saying it has to go out by hand. Doing it properly needs a `handOff` concept broader than `expired`, its own copy, and a suppressed timer — which is the ticket's deferred "send failed" card type. A named gap beats a card that reads wrong. The two lists together are asserted to account for all 26 codes the server had on transcription day, so drift shows up as a stale number. It CANNOT catch a code the server added and we never heard about — nothing here can reach that enum — so a new server code still arrives as unknown and lands on mid-thread until someone adds it. That is the safe direction; the test turns "someone adds it" into a red build rather than a release of cards on the wrong ground, which is the defect TAC-511 filed. `prose_cancellation_backstop` sits in `outsideDraft` while `commitment_cancellation_gated` sits in `obligation`, and the pair is worth reading the comment for: one is a real cancellation, the other a claim the reply cannot back up.

- **Contract-boundary test assertions — see "Cross-repo contracts" rule #5 above.** Short version: transcribe expected payloads from the ticket's `## Contract`, never from the client code; and put wire-shape assertions in `__tests__/lib/api-queue.test.ts`'s live-mode `HTTP shape` block, never the fixture-mode block (fixture mode short-circuits before `authedFetch`, so it can't observe a URL, method, header, or body). The full rationale and the TAC-310 post-mortem live with the rule — don't restate it here, it'll drift. (TAC-310.)
- **`ThreadMessageSchema` deliberately omits `.strict()`.** TAC-277's Out-of-Scope explicitly preserves forward-compat ("response schema can be extended later without breaking existing clients"). Adding `.strict()` would regress that — every future additive server field (`editedAt`, future review-state markers, anything) would make every pre-update client error on every fetch. Default Zod parse behavior (unknown fields silently dropped) is the contract. Same reasoning applies to `RecentContextEntrySchema`. If you reach for `.strict()` on a cross-repo response shape, stop — the rule of thumb is: strict only on *request* bodies your code constructs, never on *response* bodies the server constructs. A regression guard test in `__tests__/lib/api-queue.test.ts` ("getThread schema is forward-compat…") catches accidental tightening. (TAC-290.)

- **A mount is not a cold launch — and on this app a screen mount is nowhere near one.** `FrontCard` is keyed `key={top.messageId}`, so it remounts on every swipe. The tab row is not a navigator: `components/shell/top-nav.tsx` calls `router.replace()` between sibling stacks, so the queue screen unmounts and remounts on every tab return, and on every venue switch. A replace animates by default, so the root stack's tab screens carry `TAB_SCREEN_OPTIONS` (`animation: 'none'`) in `app/_layout.tsx`: a new root tab needs it too, while pushes inside a tab's own stack (the edit screen, a thread) keep their transitions (TAC-388). A `useEffect(…, [])` on a screen therefore fires constantly. The only true once-per-process seam is the root gate in `app/_layout.tsx` (`if (!fontsLoaded || session.status === 'loading') return null`), which holds the whole tree unmounted and then mounts it in one frame. Cold-launch state belongs in module scope, drained once — `consumeColdLaunch()` in `lib/entrance.ts` and `consumePendingTap()` in `lib/notifications/tap-handler.ts` are the same pattern, including the test-only reset. Resume-from-background re-runs no module scope, so it is excluded for free. A signed-out cold launch plays the entrance too, over the sign-in screen, and spends the flag doing it — which is what keeps the queue reached by signing in from playing a second one. `resolveEntranceMode` takes no auth state at all. The sign-in screens hide their own mark for the rest of a launch whose entrance played in full (`AuthFrame` reads `useEntrance().mode`, keeping the mark's space), so only one mark is ever on screen. (TAC-384; TAC-388 reversed the earlier call not to play it signed out.)
- **Staggered entrance animations are driven from ONE clock, never per-layer `withDelay`.** `lib/entrance-context.tsx` owns a single `clock` shared value; every layer's opacity/offset is a pure `'worklet'` function of it (`lib/entrance.ts`). This is not stylistic. The layers live in five components that mount at different times — `QueueCardStack` only mounts once the queue resolves, which can be after the card's 940ms slot — so per-layer clocks would start the card's rise late on a slow network and replay it on every swipe. Read from an absolute clock, a layer that mounts late finds its window gone and renders resolved, which is what makes "a slow fetch must not extend, restart or stall the entrance" hold. A layer that mounts partway through its window is different: it renders resolved only because it asks, so **every entrance layer must call `useRidesEntranceSlot(slotStartMs)` and gate its ramp on it** — skip that and it joins its fade partway, which reads as a snap. Outside a cold launch the clock is pinned past the end, so `useEntrance()` needs no provider and every consumer is a no-op — that fallback is why none of the existing component tests needed a wrapper. Anything asking "does the entrance own this layer right now?" reads `running`, never `mode`: `mode` stays `'full'` for the whole process, so a screen that mounts after the entrance (a tab return, a venue switch) would otherwise believe it was still inside it and hard-cut its ground changes. Two decisions can't be worklets because React makes them once, at the moment something mounts or changes, and both go through the pure `ridesEntranceClock` on `elapsedMs()`: whether a layer mounting now plays its slot (`useRidesEntranceSlot` — the deck of a queue that landed late, or the next card after a swipe, appears in place rather than joining its ramp partway, which would read as a snap), and whether a ground that just arrived can still ride the clock. Two corollaries: a helper called from these ramps needs its own `'worklet';` (the whole chain is registered in `__tests__/lib/worklet-directives.test.ts`), and an animation that must not be expressible as two competing writes to one value — the mark — is written as a single branch-per-segment function whose first branch is `x <= 0 → 0`. (TAC-384.)
- **The queue's empty deck sits on `resting` (clay), and that is coupled to the entrance.** `resting` is simultaneously the ground an empty queue settles on and the ground the cold-launch entrance resolves into; they must be the same value or the entrance ends by transitioning into the empty state, which TAC-384's third case forbids. `GroundScreen`'s `entranceGround` prop is the entrance's base and must be CONSTANT across the fetch — the queue screen passes `"resting"` unconditionally, never derived from `drafts`, so the clay phase is the same whether the response takes 300ms or 2s. The card's bucket ground then crossfades over it bound to `entrance.bucketDelayMs` (the card's own offset), never to the response — when the queue lands before that offset. A queue that lands after it takes the ordinary crossfade from the moment it lands: nothing knows the bucket before the data does, and riding a ramp already under way would mount the bucket nearly opaque over clay, which is a hard cut. (The ticket's original slow-fetch case had the bucket arriving 260ms before its data; it was corrected on 2026-09-14.) The bucket fade and the deck crossfade share one duration, `ground.crossfadeDurationMs` (420ms). TAC-364 collapsed the second token TAC-384 left for it; don't reintroduce one. (TAC-384, TAC-364.)
- **The native splash background must match the entrance veil, and it is invisible in Expo Go.** `app.json` had no `splash` config, so iOS shipped `SplashScreenBackground.colorset` = pure white; handing off from a white splash to a near-black veil is a hard flash that reads as a bug. The `expo-splash-screen` plugin entry now pins `backgroundColor` to `#2B1409`, roughly the veil gradient's midpoint. `/ios` and `/android` are gitignored CNG folders, so `app.json` is the source of truth and the next build regenerates them — but Expo Go paints its own splash, so this can only be verified on a dev-client or TestFlight build. (TAC-384.)
- **Nothing paints behind a screen but the navigator's light grey.** No `ThemeProvider` wraps the Stack, so every screen sits on native-stack's default `rgb(242,242,242)`. Grounds are opaque, so it never shows — except while a whole ground is partly transparent, which is exactly the entrance (the veil fading out and clay fading in cross at 200–900ms) and the reduced-motion fade. `GroundScreen` always paints `VEIL_BASE_COLOR` (near-black, from `lib/grounds.ts`) underneath — invisible under an opaque ground. Always, not while `running`: that flag ends on a JS timer, and under reduced motion the UI fade can still be finishing when it flips. The entrance overlay likewise leaves when the entrance ends rather than at the mark's last frame, for the same race. Without it the ember goes milky mid-fade and reduced motion flashes near-white — both visible on TestFlight build 40. If you add another animation that fades a whole ground in from transparent, paint something under it. (TAC-384.)

## Conventions inherited from `analog-guest`

- High-stakes flag convention (above)
- Plan → Review → Build → Review → Commit cadence
- Linear ticket template (Background / User-facing behavior / Technical approach / Acceptance criteria / Testing / Out of scope / Notes for Claude Code)

## What lives where (cross-repo)

- **In `analog-operator` (this repo):** RN screens, gestures, animations, mobile-specific UI logic, API client wrapper, Supabase auth session handling
- **In `analog-guest`:** the messaging engine, all agent runtime, database, migrations, operator-facing API endpoints (TAC-258), the Sendblue integration, all PostHog events, voice corpus management

If a build needs work in both repos (e.g. a new operator API endpoint + the UI that calls it), it gets split into two tickets — one per repo. See TAC-37 (UI) and TAC-258 (API) as the canonical example.
